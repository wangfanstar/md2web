## 1. [P1] 取消提交或放弃草稿后，prepared 操作永久阻止整库同步

**位置**：`server/operations.py:435`、`:445`、`:1479`；`server/drafts.py:246`；`server/app.py:1348`；`web/md-editor.js` 的 prepare/confirm 流程。

准备提交会立即落库一个 `prepared` 操作。`pending_commit` 把该状态纳入仓库级阻断，但取消凭据输入、离开确认界面或调用“放弃草稿”都没有取消对应操作。没有发现操作取消接口、过期清理或重新 prepare 时替换旧 prepared 操作的逻辑。

**动态复现**：

1. 创建草稿并调用 prepare_commit。
2. 调用 discard_draft，确认活动草稿数量已为 0。
3. 调用 sync_binding。

结果：同步返回 **409**，pending_commit 仍返回 **prepared**。手动更新及仓库删除/重建也依赖这项阻断。反复准备提交还可能遗留多个旧记录。

**影响**：用户没有真正执行 SVN 提交，却能使整个仓库停止更新；重启不会清除数据库记录。这是上一轮加强未完成提交保护后出现的生命周期缺口。

**建议**：为尚未开始远端提交的 prepared 状态提供取消/替换流程，并在放弃草稿时取消相关 prepared 操作。取消必须检查发起人及状态，不能把 running、uncertain、svn_committed 一并清除。补充“prepare → 取消/放弃 → 同步成功”和“重复 prepare 不遗留阻断”的测试。

## 2. [P1] 网站备份地址切换后，仍可能向旧 SVN 仓库提交

**位置**：`server/operations.py:1125`，尤其工作副本存在检查及 `:1175` 之后的提交。

网站备份固定复用 `site-wc`。只有 `.svn` 不存在时才按当前 `siteBackup.url` checkout；已有工作副本不会核对其实际 URL/UUID，也没有在配置方案切换后重新检出。之后 commit 使用的是工作副本路径，真正的远端由旧工作副本决定。

**动态复现**：

1. 对旧 URL 执行备份，让假客户端建立 `.svn` 标记。
2. 把 siteBackup.url 改成新 URL，再执行备份。
3. 捕获客户端调用。

结果：`checkout_new_url=False`、`verify_wc_info=False`、`commit_existing_wc=True`。这是调用链复现；没有实际向任何 SVN 地址提交。

**影响**：新配置显示的是新地址，备份却仍可能写到旧仓库；旧凭据仍有效时尤其隐蔽，也可能把不应发往旧目的地的资料发送过去。

**建议**：每次备份前读取工作副本实际 URL/UUID，与当前配置核对；不一致时停止并提示重新建立工作副本。也可按规范化 URL/UUID 隔离工作副本，切换时不能直接复用。

## 3. [P1] 恢复 svn_committed 操作会覆盖故障期间新增的本地修改

**位置**：`server/operations.py:524`、`:663`。

正常提交分支检查了准备时的本地 hash；但 svn_committed 恢复分支直接调用 publish_committed，后者无条件替换本地文件。磁盘故障、权限故障或人工处理期间，用户直接修改的 Markdown 会被旧的已提交内容覆盖。

**动态复现**：

1. 远端提交成功，注入本地 publish_committed 的 OSError。
2. 将本地文件改为 `NEW LOCAL CONTENT`。
3. 重试同一 operation。

结果：返回 **published**，本地新内容被旧草稿替换；远端 commit 次数仍为 1。上一轮修复避免了重复提交，但尚未保护恢复期间的本地变更。

**建议**：恢复发布时仅接受“仍等于原始基线”或“已经等于待发布内容”两种状态；其他情况返回 409，保留待恢复状态并提供差异/备份。继续保持禁止重复远端提交。

## 4. [P2] 文件发布成功后数据库记录失败，接口返回失败但文档已经改变

**位置**：`server/svn_update.py:49`–`:63`；自动同步 `server/operations.py` 中 snapshot.publish 后的数据库更新也需核查同类边界。

svn_snapshot.publish 的回滚只覆盖其内部文件写入阶段。调用方在文件发布成功后才写仓库版本和审计。此时发生 SQLite 异常，调用方返回失败，却没有恢复已经写入的文件；本地文件和数据库记录可能不一致。

**动态复现**：单文件手动更新时，将 database.audit 注入 `sqlite3.OperationalError('disk I/O error')`。实际结果为 **502**，但本地文档已经是远端新内容。

**影响**：界面显示失败、更新时间未更新，正文却发生变化；用户无法从结果判断哪些步骤已经完成。原文件备份仍存在，因此本次没有观察到备份丢失。

**建议**：设计文件发布与数据库确认之间的恢复协议。例如保留发布日志，数据库失败后明确标记“文件已更新、记录待恢复”，或回滚文件再报告完整失败。补充“文件成功 → 数据库失败”测试，不能只测试第二个文件写失败。

## 5. [P2] 单文件 SVN 更新会把非法 UTF-8 静默替换后覆盖本地文件

**位置**：`server/svn.py:165`、`:339`；`server/svn_update.py` 的 svn.cat 路径。

SVN 子进程统一采用 `encoding='utf-8', errors='replace'`。这适合容错显示诊断文本，却也用于 cat 的文档正文：非法字节先变成 U+FFFD，随后重新编码成合法 UTF-8，绕过 snapshot.publish 的编码检查。整库 export 读取原字节时会严格报错，单篇更新则不会。

**动态复现**：让受控子进程输出一个非法字节 `0xFF`，经 SvnClient.cat 读取，函数成功返回 `\ufffd`，没有抛出编码错误。后续手动更新直接对这个字符串执行 encode('utf-8') 并发布。

**影响**：远端文档为 GBK 或编码损坏时，单篇更新可能把原本可用的本地文档覆盖成乱码，同时显示更新成功。

**建议**：正文读取使用原始 bytes，再严格 UTF-8 解码；命令诊断文本可单独容错解码。错误应带文档路径，拒绝发布。补充非法字节及 CRLF 的 cat 回归测试。

## 6. [P2] 子文件夹入口与已配置仓库入口重名，构建会覆盖仓库页面

**位置**：`setup_docsify.py:859`、`:872`、`:2249`、`:2281`–`:2284`。

folder_page_names 只预留 index_all.html，没有预留全部配置仓库的固定入口名。它给冲突目录分配后缀，但后续仓库生成循环仍独立使用 repo_page_name(repo.id)。因此目录映射的去重不能保护实际仓库页面；最后的子文件夹生成循环可能覆盖前面生成的仓库入口。

**命名函数动态复现**：

```text
目录：A、C、A/B、C/Y
仓库：A → md/A；C → md/C；A_B → md/C/Y

folder_page_names['A/B'] = index_A_B.html
repo_page_name('A_B')    = index_A_B.html
folder_page_names['C/Y'] = index_A_B-2.html
```

两个不同目录仍会写到同一 index_A_B.html。命名冲突已动态确认；“仓库先写、子文件夹后写”的覆盖顺序来自构建代码检查，本次没有对当前站点执行这个破坏性场景。

**影响**：从总览点击 A_B 仓库可能打开 A/B 子文件夹，侧栏、首页及所属范围与入口标签不符。

**建议**：先保留所有仓库固定页面名称，并让仓库挂载目录固定使用自己的入口；仅对普通子目录分配后缀。生成页面、侧栏、首页和离线快照必须复用同一映射。增加嵌套仓库、下划线名称和 Windows 大小写冲突测试。
