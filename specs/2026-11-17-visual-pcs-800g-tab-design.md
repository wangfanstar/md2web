# Visual PCS 新增 800G TAB 的设计方案

日期：2026-11-17  
状态：方案阶段，本次交付 Markdown；后续实施按本方案新增页面内 TAB。

## 1. 目标与范围

在 docs/html/ref/visual-pcs.html 的“3D 通道实验”标题下新增页内标签：

- 200GBASE-R：现有实验入口。
- 800GBASE-R：基于 IEEE Std 802.3df-2024 的完整单向 TX → 链路 → RX 动画。

800G 默认展示 800GMII → 两个 Flow → 32 条 PCS lane → 32:8 PMA → 8 条 PAM4 通道 → 接收端逆过程。初版聚焦 Clause 172 PCS 与 Clause 173 PMA，以 800GAUI-8 为物理接口示例。PMD 类型用说明标识，光学链路预算、完整 800GXS 拓扑和模拟电气波形留作后续独立功能。

本方案不包含已撤回的 CBFC/LLR。界面使用中文，保留标准术语与信号名。

## 2. 依据与已核对事实

主要资料：本地 docs/pdf/8023df-2024.pdf。该文件 PDF 页码比下列正文印刷页码大 1。文档引用节号作为首要定位，避免阅读器页码偏移。

| 内容 | 设计约束 | 标准位置 | PDF 页 |
| --- | --- | --- | --- |
| PCS 架构 | 一个 800GMII 数据流分为 Flow 0 / Flow 1，合计 32 条 PCS lane | §172.2.1，图 172-2 | 199–200 |
| Block distribution | 66 位块逐块交替进入两个 Flow，发生在各 Flow 转码之前 | §172.2.4.3 | 202 |
| 转码与加扰 | 每 Flow 独立执行 256B/257B 转码、加扰；固定加扰器初值应不同 | §172.2.4.4–5 | 202 |
| AM | 每 Flow 采用 400G 形式；两个 Flow 的插入位置对应原始 66 位流的同一边界 | §172.2.4.6，图 172-3 | 202–205 |
| AM 编号 | Flow 0 对应 lane 0–15，Flow 1 对应 lane 16–31，分别使用专用编码表 | 表 172-2、172-3 | 203–204 |
| FEC | 每 Flow 分成两个 5140 位消息，再进行 RS-FEC 编码及符号分配 | §172.2.1、§172.2.4.7–10 | 200、205–206 |
| RX 汇聚 | 全部 32 lane 锁定、对齐、重排后，分为两组 16 lane，分别解码，最后交替收集 66 位块 | §172.2.5.1–8 | 207 |
| Deskew | PCS 接收端最大 Skew 为 152 ns | §172.2.5.1 | 207 |
| PCS lane 速率 | 32 条，每条 26.5625 Gb/s | §173.2 | 223 |
| 32:8 TX PMA | 每输出包含 Flow 0 的两条 lane、Flow 1 的两条 lane；时间顺序为 F0、F0、F1、F1 | §173.5.2.1 | 229 |
| 32:8 RX PMA | 接收方向为 unrestricted bit-level multiplexing，PCS 负责识别实际 lane 编号 | §173.5.2.1 | 229 |
| 8:8 PMA | 受 PAM4 symbol sequence 保持或位对交换约束，不能自由打散四条 PCSL | §173.5.2.3 | 230 |
| 标准向量 | 两个 Flow 的加扰种子、AM、编码结果可作精确校验 | Annex 172A | 269 起 |

由标准 lane 速率计算：32 × 26.5625 = 850 Gb/s 编码后总速率；8 路各 106.25 Gb/s，PAM4 对应 53.125 GBd。界面分别标识 800 Gb/s MAC 速率和编码后线速。

实现前补读基础标准 IEEE 802.3-2022 中被引用的 Clause 119/120，逐项核定 400G 的 AM 周期、位序、符号分配公式、锁定条件及错误传播。现有 200G 实现中的 8 lane、180 ns、AM 周期及字节表不能直接沿用为 800G 参数。

## 3. TAB 与交互设计

标签位于实验标题与工具栏之间，原有文章目录和章节阅读入口继续可达。每个 TAB 有独立 tabpanel、唯一 DOM ID 和状态对象。

- 使用 role=tablist/tab/tabpanel、aria-selected、aria-controls。方向键移动标签，Enter/Space 激活。
- 默认打开 200G；800G 可通过稳定锚点 #lab-800g 直接进入，刷新及浏览器前进后退可恢复选中标签。
- 切换时暂停离开的实验；重新进入时保留其选中 lane、故障与相机位置，并保持暂停，用户主动播放。
- 800G 首次打开时创建 renderer 和场景，面板可见后计算尺寸。隐藏面板停止帧循环与观察回调的绘制工作。
- 800G 提供播放/暂停、单步、速度、全景、视角拖动、重置。单步边界采用离散模型事件，连续运动仅用于显示过程。
- Flow 选择为“全部 / Flow 0 / Flow 1”；32 lane 选择器按两组各 16 排列。过滤只改变可视强调，不改变实际数据流。
- 点击模块打开阶段说明；点击数据单元显示来源块号、Flow、码字、符号和 lane。正文增加“800G 与 200G 的差异”入口。

窄屏默认显示两组 Flow 概览，点选后展开一组 16 lane。详细映射表独立横向滚动。文本、图例和数据标签避免全部同时堆叠。

## 4. 动画结构

### 4.1 发送端

1. MAC / RS / 800GMII 生成连续编号的 66 位块。
2. Block distribution 将编号 0、2、4、6…送入 Flow 0，将 1、3、5、7…送入 Flow 1。
3. 每 Flow 将四块转码为一块 257 位块，例如 F0[0,2,4,6] 与 F1[1,3,5,7]。检查器明确记录原始块序。
4. 两个独立加扰器处理各自数据。
5. 同步展示 AM 插入边界；每 Flow 的 AM 组占 8 × 257 位，使用对应 16 条 lane 的标记。
6. 每 Flow 独立完成 pre-FEC distribution → 两个 RS(544,514) 码字 → symbol distribution。
7. 输出 Flow 0 的 lane 0–15 和 Flow 1 的 lane 16–31。

两组 Flow 使用不同色系，各 lane 通过编号与色阶区分。码字采用 F0-A、F0-B、F1-A、F1-B 标记，避免把两个 Flow 的同名码字混淆。

### 4.2 PMA 与接口

默认示例映射，对物理通道 s = 0…7：

- 槽 0：PCS lane 2s。
- 槽 1：PCS lane 2s+1。
- 槽 2：PCS lane 16+2s。
- 槽 3：PCS lane 17+2s。

例如通道 0 循环承载 lane 0、1、16、17。这是符合限制的教学映射，标准允许其他满足约束的组合。

位级放大视图展示四个时隙及 PAM4 位对，按 §173.5.7 核定位序和 Gray mapping。映射切换只提供经过验证的合法配置；随机重映射按每 Flow 各选两条的约束构造，并保证 32 lane 完整且不重复。

物理通道统一标识 8 × 106.25 Gb/s PAM4。初版不提供 4 × 200G 的选项，因为该接口不属于本方案引用的 802.3df-2024 主路径。

### 4.3 接收端

1. CDR 与 RX PMA 解复用生成 32 条接收服务接口 lane，起始槽相位和接收顺序可以变化。
2. 通过 AM 公共部分搜索和锁定，通过专有部分识别 lane 0–31。
3. 对全部 32 lane 做 Deskew 与重排，显示最大时延差与 152 ns 预算。
4. 依据恢复的 lane ID 分离 Flow 0 / Flow 1。
5. 每 Flow 执行解交织、RS 解码、后 FEC 交织、AM 移除、解扰及逆转码。
6. Block collection 按 Flow 0、Flow 1 交替恢复原始 66 位流，再经 64B/66B 解码交给 800GMII / MAC。

故障解除后的锁定恢复依模型状态推进，不能仅靠计时器将所有 lane 标成成功。

## 5. 故障与诊断

| 场景 | 动画与观察点 | 验证重点 |
| --- | --- | --- |
| 单条物理通道增加延迟 | 其承载的 4 条 PCS lane 同时迟到，两个 Flow 均受影响 | 151/152/153 ns 的边界行为按标准要求及明确的教学阈值实现 |
| 单 PCS lane AM 损坏 | 该 lane 失锁，展示全局对齐状态及解码门控 | 32 lane 全局条件，不把两组视为独立完整链路 |
| 单物理通道失去信号 | 对应四条 PCS lane 缺失 | 映射与故障传播一致 |
| 符号错误 | 对应 Flow 的码字纠错或报不可纠正 | RS(544,514) 每码字最多纠正 15 个符号；覆盖 0/1/15/16 |
| 合法重映射 / RX 相位变化 | 接收顺序改变，AM 重新识别与重排 | 恢复原始块序，映射无重复或丢失 |

诊断展示全局 align_status、32 lane 的 AM lock、每 Flow 的 FEC 计数、逐 lane 符号错误、当前映射和 Deskew 裕量。MAC 收到的数据与错误标记由模拟结果生成。示意动画的时间压缩倍率明确标注，真实协议周期作为参数和说明展示。

## 6. 实现组织

现有 visual-pcs.html 将模型、Three.js 渲染、位级视图、故障和诊断集中在同一文件，并通过 window.PCS 共享状态。源码中存在 N_PCS=8、8 次循环、8 色调色板、200G 速率和 AM 参数等耦合，不能只修改一个常量来支持 800G。

拟新增以下离线文件：

- docs/html/ref/visual-pcs-assets/pcs-800g-model.js：纯模型、参数、两个 Flow、受限映射、故障与计数。
- docs/html/ref/visual-pcs-assets/pcs-800g-view.js：Three.js 场景、检查器、生命周期和 TAB 接线。
- docs/html/ref/visual-pcs-assets/pcs-800g.css：800G 专用面板、标签和窄屏样式。
- docs/html/ref/visual-pcs.html：TAB 外壳、800G 容器、章节入口及本地引用。

800G 用独立命名空间与实例；先复用当前本地 Three.js/OrbitControls。RS/GF 算法若抽取为共用模块，必须先建立 200G 前后结果对照。构建不得覆盖 ref 下新增文件，需检查 setup_docsify.py 现有复制和清理规则。

数据沿每阶段保留可追溯标识：blockId、flowId、codewordId、symbolIndex、pcsLane、physicalLane、slot。事件模型与图形位置分离，便于快进、单步及确定性测试。

## 7. 分阶段实施

1. 核定 Clause 119/120 引用及 Annex 172A 测试向量，建立参数表与映射约束。
2. 完成 TAB 生命周期和空场景，验证 200G 与 800G 切换、深链接及离线资源。
3. 完成纯 800G TX/RX 模型，先验证收发数据一致性与标准向量。
4. 绘制双 Flow、32:8 PMA、8 通道与 RX 合流动画，再接入来源检查器。
5. 接入故障、诊断、位级过程及窄屏视图。
6. 完成浏览器检查、必要回归，提交 main 并推送 origin/main。

## 8. 验收标准

- 两个 TAB 可通过鼠标与键盘访问，隐藏实验停止推进，恢复状态正确。
- 800G 正确显示 2 Flow、32 PCS lane、8 PAM4 通道、不同层次的速率及 152 ns Deskew 上限。
- 自动检查默认和所有可选 TX 映射均满足 2+2 与 F0/F0/F1/F1 时隙约束。
- 无故障时，block distribution 与 block collection 互逆，完整载荷及原始顺序一致。
- 标准 AM 表通过逐项比对；Annex 172A 的编码向量至少覆盖两个 Flow。
- 随机固定种子测试 lane 重排、相位及合法映射，恢复的数据相同。
- 关键故障正确改变相关 lane、Flow、全局状态及 FEC 计数。
- 播放、暂停、单步、速度、重置和反复切换不会产生重复帧循环或状态串扰。
- Edge/Chrome 在 file:// 和 HTTP 下检查，断网可运行。桌面与窄屏无整页横向溢出，图表及表格可读。
- 200G 原有播放、故障、位级弹窗、章节往返及汉化布局通过回归。
- 新增 JavaScript 使用 Node 做语法及模型验证；若涉及 Python 构建，按仓库要求使用 Python 3.6.8 验收。
- 公开仓库仅提交本任务源码、方案和必要测试，不将本地标准 PDF 纳入提交。

## 9. 方案边界

初版按标准建立逻辑数据流和交互教学模型。需要精确位级结果的界面应使用经测试的实际编码与位序；仅用于可读性的移动速度、绘制间距和 AM 显示频率需明确为可视化缩放。

开始实现前重点补齐两项依据：Clause 119/120 的继承参数核对，以及表 172-2/172-3 和 Annex 172A 的原页/向量交叉检查。避免依赖 PDF 表格提取后可能错位的字段。
