## 1. [P1] 本地文档移动或删除没有同步数据库，后续保存会复活旧路径

**位置**：`server/entries.py:320`–`323`；`server/operations.py:226`、`:314`–`340`。

`rename` 分支已经通过 `rename_local_entry` 更新数据库路径，但 `move` 仍只调用文件操作 `move_entry`，`delete` 只将文件移入回收站。两者都保留 `repository_documents` 中旧路径的 `published` 记录。随后保存同库任意文档时，`_materialize_repository` 会重新写出这些旧记录。HTTP 调用链在操作后只重建页面，没有补充数据库同步。

**复现步骤**：

1. 配置可写本地仓库，分别保存 `a.md`、`other.md`，使它们进入 SQLite。
2. 用文件操作接口把 `a.md` 移到 `sub/a.md`，或删除到回收站。
3. 保存 `other.md`。

**实际结果**：

```text
移动分支：old_exists=true, new_exists=true
删除分支：deleted_document_exists=true
```

移动后的旧路径重新出现，删除的文档也重新进入普通目录。删除后恢复还可能因原路径已被复活而遇到同名冲突。问题只需要普通网页保存和文件操作，不依赖故障注入。

**建议**：给本地移动、删除和恢复建立与文件操作一致的数据库更新流程；同步路径、删除状态、版本历史及清单 hash，并为失败提供回滚。不要仅在构建阶段隐藏复活的文档。

**验收**：移动/删除后保存同库其他文档，再次读取目录、数据库及回收站；旧路径必须保持不存在。恢复后再次保存，恢复文件不得被过期删除记录删除。

## 2. [P1] 单篇保存会覆盖同仓库其他文档的外部修改

**位置**：`server/operations.py:279`–`290`、`:226`、`:317`–`340`。

`local_publish_content` 的 `base_hash` 检查只覆盖当前要保存的文档，但 `_local_publish` 随后物化整个仓库。物化函数无条件以数据库正文替换每条已登记文档，没有验证其他文件的当前 hash，也没有先为其外部修改建立备份。

**复现步骤**：

1. 在本地仓库保存 `a.md` 和 `other.md`。
2. 在服务器磁盘上将 `other.md` 改为 `# externally edited`。
3. 通过正常保存流程修改 `a.md`，提供正确的 `a.md` 基线 hash。

**实际结果**：保存成功，`other.md` 被还原为数据库中的 `# local other`，外部修改丢失。只针对当前文档的冲突检查未覆盖实际被写入的全部文件。

**建议**：单篇保存只物化当前文档；确需整库物化时，对每个可能被覆盖的文件校验基线，并在冲突时保留原文件、返回明确冲突。不要把“本地 SQLite 为主库”解释成可以在另一个文档的保存操作中无提示丢弃磁盘变更。

**验收**：修改 B 后保存 A，B 字节保持原样；若执行显式整库覆盖，必须有冲突提示或可恢复备份。

## 3. [P2] 历史记录写入失败时，文件已更新而数据库回滚

**位置**：`server/operations.py:203`–`233`，尤其 `:226`–`227`。未绑定仓库的 `publish_file`（`:300`–`311`）也有先写文件再记历史的相同边界，后者本次仅做静态核查。

`_local_publish` 在 SQLite 事务内部先物化文件，再调用 `local_history.record`。如果记录历史或事务提交失败，SQLite 会回滚，但已执行的文件替换没有回滚。异常分支把操作标成 `failed` 并返回 500，界面看到的结果与磁盘状态相反。

**动态复现**：在临时数据库为 `local_document_versions` 创建 `BEFORE INSERT` 触发器，以 `RAISE(ABORT, ...)` 模拟历史写入失败，然后保存当前文档。

```text
接口层异常状态：500
磁盘正文：# saved
SQLite 正文：# local
```

**影响**：用户收到失败，但正文已经改变。下次保存时，数据库和文件 hash 不一致，还可能继续触发 `local_external_change`，使正常重试无法完成。

**建议**：复用已有快照发布的数据库确认/文件回滚模式，或者建立明确的待恢复状态和恢复记录；不能只回滚 SQL。单文件未绑定仓库的保存也应覆盖这一失败边界。

**验收**：分别注入历史插入失败、数据库提交失败、文件替换失败，验证磁盘、数据库、历史、操作状态保持一致；重试不应陷入永久冲突。

## 4. [P2] 未绑定仓库文档重命名后，已保存历史不可见

**位置**：`server/entries.py:314`–`319`；`server/operations.py:300`–`311`；`server/local_history.py:30`–`32`。

未绑定仓库文档通过 `publish_file` 保存时会记录共享历史；重命名时却走只改文件的 `rename_entry`，没有迁移 `local_document_versions.path`。历史读取按新路径精确查找，因此原有记录仍在数据库里，界面却无法通过新文件访问。

**动态复现**：在未绑定仓库的路径保存一次修改，得到原文及新文两条历史；调用 `entries.mutate(..., 'rename', ...)` 改名，再按返回的新路径查询历史。

```text
history_before=2
history_after=0
```

**建议**：将历史路径迁移从“已配置本地仓库专用重命名”抽出，供所有使用本地历史的文档共用；移动操作也需要同步迁移。按精确路径及目录边界匹配，避免误改同前缀兄弟文件。

**验收**：未绑定文档和文件夹重命名后，原版本 ID、历史条数及差异仍可在新路径查询；旧路径不能错误关联到后续同名新文件。

## 5. [P2] 普通目录点击不更新地址，章节导航不能正确分享或回退

**位置**：`web/custom-search.js:965`–`982`；相关复制入口 `web/workspace.js:321`。

最近的点击处理已扩大到 HTTP 页面，也拦截正文标题链接。命中后执行 `preventDefault`、`stopPropagation` 和 `scrollToHeadingEl`，但没有更新 URL 或浏览器历史。因此 HTTP 页面原本由 Docsify 处理的章节路由也被截断。

**浏览器复现**：点击右侧 `1. Target` 章节。

```text
链接 href：#/md/review?id=_1-target
点击后 URL：http://review.test/html/index_all.html#/md/review
点击后 scrollY：3860
```

正文确实滚动，但地址没有章节参数。如果此前已有 `?id=旧章节`，地址还会继续指向旧章节。工作台“复制链接”直接读取 `window.location.href`，因此复制到的地址不能表示刚选中的章节；浏览器也没有这次章节选择对应的历史记录。

**建议**：HTTP 下保留正确的 Docsify 锚点导航，或在统一导航函数里同步正确 URL 与历史。`file://` 的兼容处理应同时保证章节定位和可预期的地址语义。

**验收**：点击目录后地址的 `id` 与目标标题一致；复制地址在新页面能定位同一章节；前进/后退可恢复对应章节。

## 6. [P2] 手动目录仍生成无效 href，新标签打开和直接访问失败

**位置**：`web/custom-search.js:965`–`1009`，尤其修饰键提前返回及 `localHeadingId` 只在普通点击时解析。

兼容逻辑只在点击时将 GitHub 风格 slug 转为 Docsify 标题 ID，没有改正文链接的实际 `href`，也没有处理页面初始加载时的兼容锚点。Ctrl/Cmd 点击会直接返回；右键新标签打开、复制链接地址后访问也不会经过该转换。

**浏览器复现**：临时文档含 `[Go](#1-target)` 与 `## 1. Target`。

```text
实际标题 ID：_1-target
渲染后的手动链接：#/md/review?id=1-target
直接打开该链接后的 scrollY：0
```

同页普通点击可以被兼容代码修正，但复制或新标签打开仍停在顶部。这与上一条“正确章节 href 被拦截后不更新地址”是两个不同缺口，需要分别验证。

**建议**：渲染完成后解析并规范化同页手动目录的 `href`，保留真实可分享的 Docsify 标题 ID；同时兼容直接进入旧 slug 链接。不要依赖捕获点击事件作为唯一修复。

**验收**：数字开头、中文、标点、重复标题的手动目录在普通点击、Ctrl/Cmd 点击、右键新标签、复制地址及刷新后均定位正确标题。

1. 先统一本地文件操作与 SQLite 生命周期，处理问题 1、2，避免继续复活和覆盖内容。
